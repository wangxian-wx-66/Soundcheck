# 字段名泄漏二次修复（CommentInfoList + L3 裸码）

日期：2026-09-14 | 触发：用户线上真 key 选题雷达实测（问题：内存显卡什么时候回归正常价格啊？）

## 现象

1. 争议预演第 3 条「推导」佐证出现：「评论区相关性弱，**CommentInfoList未提供直接反驳**」——接口字段名直接漏进用户可见文本。
2. 近期讨论列表显示「273赞 **L3**」——权威等级裸码，无中文说明，用户无法理解。
3. 用户同时对本次雷达报告整体语气提出验收问题（结论：达标，见下）。

## 根因

| # | 根因 | 位置 |
|---|---|---|
| 1 | 争议预演 `objections[].source`（佐证/推导依据）**未过 humanize**——上一轮（v2.22）只覆盖了 objection/response，漏了 source | lib/pipeline.mjs 落库映射 |
| 2 | `meta.note` 同样未过 humanize（防御性补上，本次未见泄漏） | 同上 |
| 3 | humanize 正则④的字段名名单只有 JSON 键名（evidence_level/rating/unique 等），**没有接口名**（CommentInfoList/question_answers/zhihu_search 等）——而 system prompt 的证据等级定义里明确写着「L3：CommentInfoList 真实评论」，LLM 自然会在 source 里复述这个词 | lib/pipeline.mjs humanize() |
| 4 | UI 渲染近期讨论 meta 时直接拼裸 `authority`（值形如 "L3"）；且标杆 chip 的 `L${authority}` 在值已带 L 前缀时会渲染成「LL3 权威」 | public/app.js / lib/pipeline.mjs collectEvidence |

## 修复（4 处代码 + 1 处 prompt）

1. **humanize 正则④名单扩充**：加入 `CommentInfoList|question_answers|zhihu_search|global_search|hot_list`（环视守卫不变：仅后随中文时剥除，正常英文句子不误伤）。
2. **source 字段补 humanize**：`humanize(String(o.source || '')).slice(0, 200)`。
3. **meta.note 补 humanize**（防御性，默认值文本经规则验证零改动）。
4. **UI 两处权威码统一**：
   - app.js 近期讨论：`273赞 L3` → `273赞 · 权威 L3`（去重 L 前缀）
   - pipeline.mjs 证据 chip：`L3 权威` → `权威 L3`，并修复 `LL3` 双前缀隐患
5. **prompt 禁令扩充（层 1）**：禁止字段名/接口名清单加入 CommentInfoList、question_answers，并给出中文替代表述（「真实评论」「默认排序」）。

## 验证

- `node --test tests/pipeline.test.mjs tests/opportunity.test.mjs`：**40/40 通过**（新增 1 条测试：「接口名泄漏剥除」，锚定本次实测原文「CommentInfoList未提供直接反驳」）
- 修复后该句渲染为「评论区相关性弱，未提供直接反驳」

## 语气验收结论（用户问题 1）

本次雷达报告正文符合计划书三层文风治理要求：完整短句、结论先行、无括号嵌套/斜杠枚举/名词堆叠；「别再去补一遍AI挤占产能的机制，那个赛道已经挤满了377赞的标杆答案」等表述达到「懂行的朋友给建议」的目标语感。仅有的观感问题就是本次修复的两处代码泄漏，非模型文风问题。
