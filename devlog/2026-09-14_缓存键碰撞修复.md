# 2026-09-14 · qa_cache 缓存键碰撞修复（跨问题错误命中）

> 计划书 v2.20 → v2.21 | 触发：用户真 key 实测发现 L1 标杆序返回机器学习内容与罗永浩草稿完全不匹配
> 排查手段：SQLite events 表事件流取证（search_start 查询词 + benchmark_start URL + cached 标志）

## 一、根因（非 mock 硬编码，是缓存键真 bug）

`searchCacheKey(apiType, { query, count, filter, sort })` **解构只取四个字段**，而 `questionAnswers` 传入的是 `{ questionUrl, limit }`——两字段被整体丢弃，导致**所有问题的 question_answers 缓存键完全相同**（`sha256({apiType, apiVersion})`）。

时间线还原（事件表取证）：
1. 2026-09-13 下午真 key 测试：机器学习问题的标杆回答落 qa_cache（唯一键）
2. 2026-09-14 用户以「罗永浩 × 野人先生」草稿跑开麦评审：检索 1-6 轮全部真实（罗永浩/西贝/海底捞查询词，adopted 10，cached false），定位到问题 `2082497943508973001`
3. question_answers 查缓存 → **命中昨天那份机器学习回答**（benchmark_done `cached:true` 铁证；qa_cache 存储的 question_url 是 `2009226356785947031`，与本次请求 URL 不同——同一键下的张冠李戴）
4. 真实 LLM 诚实识别「接口返回与该问题完全不匹配」并在 meta.note 声明 L1 降级——诚实纪律工作正常，但缓存层喂了毒数据

同族隐患一并修复：hot_list 的 `limit`、global_search 的 `searchDB` 也被同函数丢弃。

## 二、修复

- `searchCacheKey` 改为 `JSON.stringify({ apiType, ...params, apiVersion })` 序列化全部入参
- 键格式兼容性核查：zhihu_search/global_search 调用方新旧键**完全一致**（JSON.stringify 本就丢弃 undefined 字段）→ 已有搜索缓存全部有效；question_answers/hot_list 键格式变更 → 旧条目自然孤儿化（不可达）
- 数据清理：删除用户库 qa_cache 旧键条目 1 条（碰撞键写入的毒数据）

## 三、测试

- 单测 +2（45/45）：①缓存键区分问题 URL 与 limit（本 bug 直接回归）②端到端——mock fetch 按问题返回不同答案，断言两问题各调一次接口、无跨问题缓存命中
- 烟测 14/14

## 四、经验教训（写入计划书风险表）

- **缓存键必须覆盖全部入参**：v2.4 曾修过「仅 query 哈希跨条件命中」，但修法是往解构里加字段而非序列化全部——同类 bug 二次复发。正确姿势是白名单反转：默认全量序列化，显式排除无需入键的字段
- **events 落盘的价值兑现**：无事件流取证此问题几乎无法定位（用户第一反应是「mock 硬编码」，实际 mock 零涉及——检索返回 10 条即可排除 mock，mock 只返回 3 条）
- LLM 的诚实纪律（meta.note 声明降级）在基础设施出错时提供了第一道告警
