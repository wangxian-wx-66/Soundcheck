## 一、产品一句话

知乎答主按下发布键之前，AI 帮你预演这次开麦——已有回答覆盖了什么、你的真正增量在哪、评论区会怎么杠你。

**双模式定位**：

* **开麦评审**：粘贴草稿 → 增量战报（面向发布前）

* **选题雷达**：输入问题 → 论点地图 + 空白点（面向写作前，零门槛入口）

**核心主张**：在 AI 生成内容泛滥的时代，帮真人创作者在开麦前做一次「信息增量体检」，让「发布」这个动作重新变得郑重。

**定位纪律**（写进计划书的边界）：

* 讲「发布前增量对比引擎」，不讲 AI 味检测（那是红海，我们的场景是空白）

* 讲「助力真人创作者」，不讲「对抗 AI 内容」（契合官方叙事，周源财报原话：「真人创作的独特价值在 AI 时代进一步凸显」）

* 目标用户明确为**认真答主**（垂直领域专业创作者），不宣称覆盖全体答主

## 二、已核实的可行性结论（五路独立调研汇总）

### 2.1 API 前提 ✅（官方 skill 包内 http-api.md + CLI 0.6.0 capabilities 实查 + **2026-09-12 真机实测**，详见 devlog/2026-09-12_API实测报告.md）

| 能力              | 结论                                                                                                                                |
| --------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `zhihu_search`  | ✅ 返回 `RankingScore`（相关性）+ `AuthorityLevel`（权威 1-4）+ `VoteUpCount` + 带 utm 溯源 `Url`。Count 上限 10、无分页。**实测（30 条样本）**：延迟 0.7s/次；CommentInfoList 命中率 **37%**（规律：CommentCount>0 几乎必返，29/30 一致）；RankingScore 实际范围 1.29-2.14（非 0-1 归一化，恒降序）；AuthorityLevel 仅见 L3/L4（L4 约 60%）；摘要 289-1078 字符 |
| **搜索结果偏近期低赞（实测关键发现）** | ⚠️ 30 条结果最高赞 554、**零条上千赞**、21/30 赞数 <10 → 搜索返回「近期相关内容」而非「高赞标杆」→ **覆盖分析必须双证据链**：zhihu\_search（富字段：赞数/权威/评论）+ question answers（社区默认序≈标杆序）。「对比高赞回答」叙事降级为「对比已有回答（标杆序 + 近期讨论）」，不伪造高赞口径 |
| `global_search` | ✅ Filter 高级语法（host/publish\_time），Count 最大 20                                                                                     |
| `hot_list`      | ✅ 实测：字段 Title/Url/ThumbnailUrl/Summary（薄）。CLI 仅 --limit 1-30，**无时间范围参数**（手册的「最近 N 小时」未暴露，不指望）。100 次/天                                            |
| 直答              | ✅ OpenAI 兼容，`zhida-fast-1p5 / zhida-thinking-1p5 / zhida-agent`。**仅支持 model/messages/stream，无 tools** → 不能当 Agent 大脑，只做彩蛋。**5,000 次/天（9/13 复测，官方自 100 放宽）**——L4 证据层可适度使用，仍标注「AI 转述」 |
| `ContentText`   | ⚠️ 是摘要不是全文 → 报告卡明示「判断基于检索摘要，附原文链接」                                                                                                |
| **`question answers`**（CLI 0.6.0 新能力，http-api.md 未收录） | ✅ **已实测（20 条样本）**：默认排序≈社区标杆序（老牌经典回答排前，answer ID 53910077/22465357 等位列头部）——正是搜索缺的「标杆覆盖」。⚠️ 字段极薄：仅 ContentType/ContentToken/Url/Summary，**无赞数/作者/评论**；摘要 76-316 字符（比搜索摘要薄 2/3）；offset 分页 IsEnd=false。**额度实测 100/天（独立额度项）** → 覆盖分析标准步骤 + 结果缓存（问题 URL → 回答列表，老问题标杆变化慢，TTL 可设 7 天） |
| **`quota`**（CLI 0.6.0 新能力） | ✅ 实时额度查询，不消耗额度 → 额度账从「文档推断」升级为「运行时可核实」，可做额度余量展示/熔断 |
| `question recommend` / `me comments` / `me stats`（CLI 0.6.0 新能力） | 选题雷达潜在数据源（个性化问题推荐）/ P3 复盘模式数据基础（评论 + 创作统计） |
| **OAuth 用户数据（0.7.2 官方文档确认，2026-09-13）** | ✅ 黑客松 OAuth：基础信息 `GET openapi.zhihu.com/user`（仅 Bearer OAuth token，无需 Access Secret；uid 为 int64 须无损解析）；五项用户数据接口（创作列表/关注/收藏夹/收藏内容/近期收藏，Bearer Access Secret + X-OAuth-Token + X-Request-Timestamp）额度 10,000/天；`state` 已支持原样透传（须密码学随机 + 会话绑定 + 原子消费，脚手架已实现）；⚠️ 创作列表仅标题+摘要，四项创作接口不可 OAuth 代查 |
| **L2 定向补强（v2.7 实测定稿）** | ✅ 双策略验证：**策略 A（问题标题搜索）**命中目标问题近期回答 3/10（富字段均值 1019 字符，与 question answers 互补：同问题近期回答一边有位次无内容、一边有内容无位次）；**策略 B（标杆摘要关键词搜索）**返回同主题深度内容 10/10（L4 权威为主、均值 1002 字符、最高赞 172）。⚠️ **两策略均 0 命中标杆回答本身**（搜索索引偏近期，2016-17 年代老回答不可搜得）→ L2 定位为「标杆论点的社区深度验证器」：标杆摘要给出论点关键词 → 二次搜索验证该论点的社区覆盖深度（论点级证据 ~1000 字符） |
| **全文可得性（v2.7 六路核查）** | ❌ 他人内容全平台无全文端点：搜索/热榜/用户内容接口字段均为摘要（文档+实测双重确认）；`me content`（content_detail）实测可拿**本人**内容 Body 全文 HTML，**他人内容被服务端归属校验拒绝（Code 10001）**；zhida-agent 可生成式转述指定回答（实测 23.6s/1153 字符）但引用细节不可交叉验证 → 仅作末级证据且明示「AI 转述」；网页爬取为手册红线禁止。**~~产品机会：P3 复盘模式可经 OAuth 拿本人回答全文（9/13 OAuth 验证）~~ ❌ 官方 0.7.2 文档（2026-09-13）明确否定：me content 等四项创作接口仅支持 Access Secret 所属账号，不能通过 X-OAuth-Token 代查——P3 复盘定稿摘要级（OAuth 用户创作列表：标题+摘要）** |

**额度口径（2026-09-12 实名认证后 CLI `quota` 实测，权威口径；2026-09-13 复测修正直答）**：zhihu_search / global_search / **直答** 各 **5,000 次/天**（直答为 9/13 复测官方放宽，原 100）；question_answers / hot_list / 创作能力各 **100 次/天**；知识库 500/天；小工具 10/天；用户数据 10,000/天。额度按 API 分项独立计数，`quota` 命令实时精确（9/12 实测 11 次搜索 + 9/13 复测 1+1+1 消耗，对账均分毫不差）。两个注意：①同账号所有 Access Secret 共享额度池，页面测试与 API 同池；②手册承诺的「token 补贴 + API 专属额度」具体口径 9/13 开幕式 API 讲解环节确认后回填。

**关键升级（实测校准）**：`CommentInfoList` 让争议预演**有据可依**——预演的反驳模式来自同问题下真实精选评论，不是模型幻觉。零额外 API 成本（同一次搜索返回）。**实测命中率 37%（每 10 条搜索结果约 3-4 条带真实评论）**：命中时标注「真实评论证据」；未命中时降级为「基于论点推导的潜在质疑」并明示证据等级——不伪造评论佐证。

### 2.2 创新性 ✅（四路威胁扫描通过）

* 泛内容同质化检测（contentany）：边缘竞品，面向公众号/百家号，非知乎站内对比

* AI 味检测（腾讯朱雀等）：成熟红海，主动避开

* 知乎官方（AI 看山 11.0）：覆盖问答/搜索/创作辅助，无「发布前增量分析」

* 黑客松同题（S1 138 项目 + 本届公开讨论）：未发现同类

**官方期待方向原文命中**（计划书直接引用）：

* 「Agent 在社区中的新角色，如……**观点陪练**」→ 争议预演

* 「**Agent 与 Agent 之间的新型社区互动模式**」→ 主审 Agent × 杠精 Agent 双角色

* 「立足知乎知识社区的 AI 学习能力，如摘要、解读、**观点提炼**」→ 覆盖分析

### 2.3 实用性 ✅（中等痛点 + 三针修正后中上）

* 新回答被老回答淹没？不成立——知乎有最新排序，2024 后强化深度互动权重，有增量的回答更可能被推荐（这是我们的价值论据）

* 官方已有类似工具？不成立

* 三针：双模式入口（解决粘贴门槛 + 呼应评分表「效率」）/ 目标用户收窄 / 首页隐私承诺（草稿仅存于浏览器本次会话 sessionStorage，后端与数据库不落草稿，分析时匿名发送 AI 检索比对；报告卡不含草稿全文）

### 2.4 LLM 技术可行性 ✅

单次分析 1.5-3 万 token 输入，128K 上下文轻松容纳，成本 <$0.1/次。两条铁律：草稿放 prompt 开头（lost-in-the-middle）；schema-enforced JSON mode（无约束解析失败 8-15%，有约束 <0.1%）。

## 三、产品架构 v2.2

### 3.1 主管线（单管线；v2.4 起 run_id 贯穿全链路）

```
入口 A：选题雷达（只输入问题/热榜点选）
入口 B：开麦评审（粘贴草稿）
        ↓
分配 run_id（贯穿全链路：SSE 事件序号 → 报告落库 → 战报卡 URL 回访）
        ↓
┌─ 主审 Agent 循环（自有 LLM + function calling，预算 6 次工具调用）─┐
│ 1. 解析（草稿→论点 / 问题→子议题）                                  │
│ 2. 自主决定检索词 → zhihu_search / global_search                     │
│    └ 定位到目标问题后【标准步骤，非可选】：question answers 拉该问题 │
│       默认序（≈社区标杆序）前 20 条回答——L1 证据层（见下方四层链）  │
│ 3. 观察结果 → 证据不足则自主改写检索词再搜；充分则退出               │
│    └ L2 定向补强【标准步骤】：预留 2 次搜索预算给标杆关键词——       │
│       ①问题标题搜索：补目标问题近期回答富字段（实测命中 3/10）      │
│       ②标杆摘要关键词搜索：验证标杆论点的社区覆盖深度（实测 10/10    │
│       同主题深度内容，~1000 字符论点级证据）                         │
│ 4. 证据加权：搜索结果用 RankingScore×AuthorityLevel×VoteUpCount，   │
│    question answers 用默认序位次（标杆序即社区共识排序）             │
└──────────────────────────────────────────────────────────────┘
        ↓
四层证据链（v2.7 实测定稿，报告内每个判断标注证据等级）：
  L1 question answers   标杆序 + 薄摘要（~219 字符）→ 谁是标杆、论点关键词
  L2 定向补强搜索       富字段 ~1000 字符 → 标杆论点的社区深度覆盖验证
  L3 CommentInfoList    真实评论（37% 命中）→ 争议证据
  L4 zhida-agent 转述   仅当 L1-L2 仍不足，标注「AI 转述，非一手证据」
        ↓
三段输出（schema JSON）：
  ① 覆盖分析（已有论点谱系 = 标杆回答主谱 + 近期讨论补充，附原文链接，
     每个论点块标注证据等级：L1 标杆序 / L2 深度验证 / L3 评论）
  ② 增量定位（已被覆盖 / 独有增量 / 相邻空白 + 如何放大）
  ③ 争议预演（基于真实 CommentInfoList 模式预测反驳 + 应对；
     字段未返回时降级为推导型质疑并标注证据等级）
        ↓
「开麦战报卡」→ 一键分享海报
```

### 3.2 多 Agent 设计（本次升级核心）

**主审 Agent + 杠精 Agent 双角色**：

* 主审：研究型，负责检索与三段分析（如上）

* 杠精：对抗型，独立审阅草稿，专门找茬——预测最狠的 3 条反驳，引用真实评论模式佐证「这个社区真的会这么杠」。**证据分级（v2.4）**：CommentInfoList 命中 → 标注「真实评论证据」；未命中 → 降级为「基于论点推导的潜在质疑」，战报卡明示证据等级，不伪造评论佐证

* 两者的分歧点（如主审认为严谨、杠精认为样本不足）**直接呈现在战报卡上**——评委看到一个「内部有分歧的评审团」，比单 Agent 输出可信得多

* 技术成本：一次额外 LLM 调用（同管线并行）+ 研究台多一个角色列

### 3.3 功能晋级阶梯（Feature Gates）——「更进一步」的正确姿势

vibe coding 让产能上移，但**完成度占 25%，任何未达「评委可上手」的功能都是负资产**。解法不是定死范围，而是设晋级门槛：

| **P0-B 必须** | 战报卡（URL 带 ?report=run\_id 可回访）/ OAuth 登录                | G1 绿，9/14 12:00 随 G2 一并验收      |
| **P0-C 必须** | **稳定性四件套**（详见 §六）：草稿暂存 / 报告落地 / SSE 续传 / 并发闸门 + 10 并发冒烟 | G1 绿，**G2：9/14 12:00** 一并验收 |
| **P0-D 必须** | 研究台 SSE 可视化                                        | G2 绿，**G3：9/14 16:00**（P0 完全体全绿） |

| **P2 冲刺** | 分享海报 / 热榜机会榜：预计算「今日热榜上还缺好回答的 3 个问题」（hot\_list + 少量搜索，每日缓存）/ 演示问题全链路预热 | G4 绿，9/14 24:00 前                  |
| **P3 余力** | 复盘模式（OAuth 拉已发布回答做增量复盘，**v2.8 定稿摘要级：~~me content 若支持 OAuth token 代表调用，可拿本人回答全文而非摘要~~ 官方 0.7.2 文档否定 OAuth 代查，复盘用 OAuth 用户创作列表（标题+摘要，10,000 次/天额度富余）+ me comments（本人账号评论模式））/ 双草稿 A/B 对比 / 看山皮肤彩蛋        | 9/15 凌晨仍有余力才做         |
| **硬冻结**   | 一切功能                                                | 9/15 00:00，之后只修阻断 bug |

**明确否决的方向**（判断依据，写进计划书防 scope 失控）：

* 浏览器插件（嵌入知乎编辑器）：体验最优但评委需安装，手册明示安装类作品有理解成本，赌完成度分不值

* RAG / 向量库 / 知识图谱：长上下文已覆盖需求，基础设施是纯负担

* 移动端：无理由

## 四、视觉系统（80/15/5 预算分配）

**原则：80% 预算给输出物（战报卡），15% 给过程（研究台），5% 给界面。** 界面只在 Demo 被看 30 秒；战报卡会被截图传播、挂项目广场反复被看，直接喂人气奖。

### 4.1 开麦战报卡（输出物，传播核心）

## 五、Vibe Coding 执行模型（本次新增核心）

以 AI 生成代码为主的 48h，瓶颈不在写码，在**集成、调试、验证、品味**。执行模型随之改变：

### 5.1 Spec Card 驱动

每个模块一张规格卡，人写卡 → AI 生成 → 人验证：

```
模块：zhihu_search 适配层
输入：query string, count
输出：标准化 Item[]（含 RankingScore/AuthorityLevel/CommentInfoList）
接口：async searchZhihu(query, count) → Item[]
验收（先写）：
  1. mock 测试：给定 fixture JSON，字段映射正确
  2. 缓存：同 query 二次调用不发起 HTTP
  3. 30001 错误码 → 抛 RateLimitError
依赖：无（叶子模块，最先做）
```

### 5.2 构建顺序（为 AI 代码量优化）

叶子模块（数据层/渲染层，无依赖，可并行生成）→ 集成层（Agent 编排）→ 串联调试。每个 gate 预留 30min 专门还集成债。

**稳定性是设计出来的，不是返工补出来的**：run_id、SSE 事件序号、并发闸门的接口签名在 P0-A 的 spec 卡里一次定死，管线第一版就带着跑——9/14 上午的 6 小时只写实现（暂存回填、报告落库、重连回放、闸门计数），不返工主管线。

### 5.3 人力分配（预计单人或双人）

* 40% 写 spec + 迭代 prompt

* 35% 集成调试 + 验收测试

* 25% 品味打磨（视觉细节/文案）

### 5.4 原创性核验（规则要求 × vibe coding 天然契合）

规则原文：「创作过程建议留存 AI 交互记录、设计底稿、开发日志等素材」。vibe coding 的全部 AI 对话记录、prompt 底稿、spec 卡**就是**核验材料——建一个 `devlog/` 目录全程自动归档，零额外成本。

### 5.5 AI 代码风险与对策

| 风险           | 对策                              |
| ------------ | ------------------------------- |

### 额度账（2026-09-12 CLI `quota` 实名后实测口径）

| 资源            | 单次分析消耗             | 上限（实测）  | 结论           |
| ------------- | ------------------ | ------ | ------------ |
| zhihu\_search | ≤6 次（含 1 次失败重试）   | **5,000/天**（高于手册 1000；8 路并发实测零限流，延迟 0.7s/次） | 800+ 分析/天为**额度理论上限**；实际体验容量由并发闸门保证（见下）。⚠️ 同账号所有 Access Secret 共享额度池，页面测试与 API 同池 |
| question\_answers | 定位到问题后 1 次（limit 20，**结果缓存 TTL 7 天**——老问题标杆变化慢） | **100/天（实测）**，额度独立 | **管线最紧约束**：无缓存时 100 分析/天；有缓存（不同用户答同一热门问题命中）实际更高。覆盖分析标杆数据源 |
| hot\_list（P2） | 每日预计算 1-2 次        | 100/天  | 富余           |
| 直答（L4 彩蛋）     | ≤1 次               | **5,000/天（9/13 复测放宽）** | 富余        |
| 自有 LLM        | 1-2 万 token（+杠精翻倍） | 按 key；手册承诺比赛期间 token 补贴（口径待开幕式确认） | <$0.2/次      |

> 额度与成本均为**最坏情况口径**（含 1 次失败重试）。**额度余量运行时可核实**：CLI `quota` 命令实时查询且不消耗额度 → 启动自检时打点，低于 20% 触发降级（跳过杠精二次调用、命中缓存优先）。并发保护三件套（single-flight / 断线续传 / 上游在飞上限）保证 N 人同题只烧一次、断网重连不重烧——这是额度理论上限变成可承诺容量的前提。9/13 开幕式若公布黑客松专属额度口径，以官方为准回填。

### 稳定性与数据架构（v2.4 新增，P0-C 硬性验收）

**设计原则：报告是产品资产，不能只活在一条 SSE 连接里；如果用户断线/刷新的代价是重烧 6 次搜索 + LLM 调用，这个产品在评委高峰必死。**

四件套（每件 ≤2h，spec 卡先行，接口在 P0-A 定死）：

| #   | 防什么                 | 方案                                                                                                          |
| --- | -------------------- | ----------------------------------------------------------------------------------------------------------- |
| ①   | 切页/刷新丢草稿（按原方案必然发生）  | 前端 sessionStorage 防抖 500ms 暂存草稿+问题，回页/刷新自动回填（关标签页即清，与隐私承诺一致）；双模式切换用 hash 路由，组件不卸载                       |
| ②   | 报告只活在当前页面（刷新即丢）     | 每次分析生成 run\_id；三段 JSON 完成即落 reports 表（LRU 1000，无 TTL，覆盖全评审期）；战报卡 URL 带 `?report=run_id`，刷新/分享/项目广场挂载均可回访 |
| ③   | SSE 断线 → 任务重跑烧额度    | 每条事件带自增序号；重连带 Last-Event-ID 回放缓存事件；任务状态机 pending→running→done/failed；客户端断开时服务端**跑完落库再等重连**（额度已烧，结果必留），绝不重跑 |
| ④   | 评委高峰打爆 0.5C/1G 单容器   | 全局信号量：同时活跃分析 ≤6，超出排队显示「前方 N 人」；single-flight：Map\<cacheKey, Promise\> 合并同 key 并发；zhihu\_search 在飞 ≤4、LLM 并发 ≤4；Agent 单轮 60s / 全管线 5min 时间熔断 |

**缓存键修正**：`sha256(api_type + query + count + filter + 时间范围 + 排序 + api_version)`——仅 query 哈希会跨条件错误命中（不同 count/filter/时间窗共享到错误证据）。

**SQLite 工程细节**：

* 单库 `/data/soundcheck.db`，建表写在启动自检里：打不开/损坏 → 改名 `.corrupt` 备份 + 重建（均为可再生数据，重建不致命）
* `PRAGMA journal_mode=WAL`——SSE 长连接读 + 报告并发写必需，默认 journal 模式会锁库
* 容量边界：单活跃分析预估 ~40MB（草稿 + 6 次检索结果 + 上下文构建），6 并发 ≈ 240MB 堆 + Node 基线，1G 余量充足；冒烟以 `--max-old-space-size=768` 验证，OOM 则闸门降至 4

**演示预热（新增流程）**：9/14 20:00-24:00 用 3 个固定演示问题跑全链路一遍，搜索缓存 + 报告全部落库——评委自助体验秒出、路演 Demo 稳定。诚实边界：命中缓存与实时链路走同一代码路径（只是不等检索），路演备一个新题现场跑实时，主动说明区别，不伪装。

**已知边界（诚实标注，不伪装生产级）**：OAuth 会话仍在内存——48h 冲刺期内每次重部署全员掉线重登一次（可接受）；**评审期 9/15-9/23 冻结重部署**，杜绝掉会话/丢缓存。

### 部署方案（Sealos，已定稿 2026-09-12）

**结论：Sealos 容器部署，单容器全栈，不绑域名，不用阿里云学生机。**

**选型裁决**：

| 方案 | 裁决 | 一句话原因 |
| --- | --- | --- |
| 阿里云学生机 | ❌ 否决 | 无域名 → 裸 IP 拿不到正规 HTTPS 证书；自签证书 = 评委浏览器红色警告 + OAuth 跳转中断；国内服务器绑域名需 ICP 备案（1-3 周起），来不及 |
| Cloudflare | 次选 | 官方点名平台，但 `*.pages.dev` / `*.workers.dev` 国内访问不稳定，评委 Demo 打不开是灾难 |
| Zeabur | ❌ 否决 | 免费共享集群 2026.3 起停止接受新项目，最低 $5/月（官方 changelog：zeabur.com/changelogs/phasing-out-shared-cluster） |
| ClawCloud Run | ❌ 否决 | 已宣布即将停止运行 |
| **Sealos** | ✅ 选定 | 官方点名平台；部署即自动分配 `*.sealos.run` 二级域名 + HTTPS（满足「不绑域名」）；容器常驻，SSE 长连接不被 serverless 超时掐死；国内可直连；注册送免费额度，9/12-9/23 全程成本个位数 |

**否决学生机的结构性原因**：OAuth 回调是硬约束——官方 `configure_callback.mjs` 源码强制校验回调地址必须为**公网 HTTPS**（localhost / 私网 IP / HTTP 一律拒绝，且必须以 `/auth/callback` 结尾）；官方边界文档原话：「本地地址只能预览页面……真实联调必须部署到 Cloudflare、Sealos 等平台」。

3. 拿到 `https://xxx.sealos.run` 后登记回调：
   ```powershell
   node c:\Soundcheck\scripts\configure_callback.mjs --project-dir c:\Soundcheck --redirect-uri https://xxx.sealos.run/auth/callback
   ```
4. 回调地址登记（9/13 10:00 后完成）：官方项目提交页「创建项目」→「知乎登录回调地址」填 `https://xxx.sealos.run/auth/callback`（用 OAuth 登录则必填，否则用户无法完成授权），与 configure_callback.mjs 登记**一模一样**（协议 / 域名 / 路径 / 尾部斜杠完全一致）

| 坑 | 对策 |

### 网络环境预案（国内镜像规范）

48h 内**网络问题是纯粹的工程风险**（下载超时、镜像中断、依赖装不上），不是可以「等一等」的问题——安装失败直接烧冲刺时间。

**统一原则**：

1. **默认走国内镜像，不要先试境外再失败再换**——预配置一次，全程生效，省去每次失败重试的时间
2. **只用白名单镜像源**（安全要求：来历不明的镜像可能被投毒，比赛期间引入供应链风险不值得）
3. Dockerfile 里**写死镜像源**，不依赖本机配置（Sealos 构建环境不会继承你的 npm config）

**白名单与用法**：

| 资源 | 镜像 | 用法 |
| --- | --- | --- |
| npm 依赖 | npmmirror（原淘宝源，阿里云运营） | `npm config set registry https://registry.npmmirror.com`；Dockerfile 内：`RUN npm config set registry https://registry.npmmirror.com && npm ci` |
| Node 安装包 | npmmirror 的 node-release 镜像 / 华为云 | 本机装 Node 22 时直接用 |
| Docker 基础镜像 | 阿里云容器镜像服务 / 网易蜂巢（163） | `FROM node:22-alpine` 前配 registry mirror；或在 Dockerfile 用 `[registry]/library/node:22-alpine` 形式 |
| GitHub 代码 | ghproxy 类加速前缀 / Gitee 导入 | 紧急拉代码用；仓库可同步一份到 Gitee 备用 |
| Sealos 拉取 | 平台内置镜像代理 | Sealos 部署时用平台内置的镜像加速，控制台选择即可 |

**执行时机**：9/12（今天）部署前完成预配置——本机 npm 源 + Dockerfile 双写死，一次到位。
